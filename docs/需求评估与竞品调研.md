# 多格式动效预览工具：需求评估与竞品调研

调研日期：2026-10-29。阶段：需求发现，尚未进入产品方案定稿或工程实现。

## 1. 已确认的产品约束

- 开源工具，先由团队和朋友使用，之后逐步向公开用户开放。
- 使用 GitHub Pages（github.io）部署；现阶段不部署服务器，不引入后端依赖。
- 场景来自语聊房社交 App：进场、礼物、连送、头像框、麦位形象、宠物、表情和 UI 动效。
- 核心诉求是方便预览、检查细节、理解素材信息及实际可用的动态能力。
- 本阶段交付研究、需求优先级、边界与验证方案，不继续实现网页。

## 2. 研究方法与可信度

本次为公开资料桌面调研：查阅产品官网、官方文档、开源仓库和公开 issue。没有开展访谈，没有用相同素材对所有竞品进行端到端测试，也没有可靠市场规模或使用频率数据。

证据分三类：

1. **公开能力**：供应商或项目明确写出的功能。可证明已有供给，不能证明实现质量。
2. **问题信号**：用户公开反馈或官方 FAQ。可证明有人遇到问题，不能推导普遍发生比例；历史问题不等于当前版本仍可复现。
3. **产品假设**：针对语聊房工作流推导的机会。需要观察实际使用后才能确定优先级。

## 3. 初步判断

这个项目可行，但“同时支持多种格式”已经存在直接竞争。更值得验证的定位是：

> 面向语聊房、直播团队的开源动效检查工具：导入素材后，快速看清画面、时间、动态占位内容及可能的交付问题，并把检查结果交给同事复现。

GitHub Pages 适合提供这个工具的静态入口；素材在使用者浏览器里处理。初期价值应通过减少工具切换、减少往返确认验证，而不是先追求七类格式全覆盖、格式转换或在线素材管理。

## 4. 竞品与替代方案

| 对象 | 已查到的公开能力 | 对本项目的启示 | 本次证据边界 |
| --- | --- | --- | --- |
| [SVGA Preview](https://svga.dev/svga-preview) | 拖入或选择 SVGA 文件、案例入口和版本转换入口 | 导入到看到动画的路径要短，可作为上手体验参照 | 未上传真实文件，不据页面静态内容断言其没有其他检查能力 |
| [PAGViewer](https://pag.io/docs/zh-CN/pag-viewer.html) | 桌面预览、文件信息、文本和图片替换、性能分析 | 专业检查已有较成熟基准；网页的便利不能靠降低信息可信度换取 | PAG 专用桌面工具；未实际运行 |
| [LottieFiles Editor](https://lottiefiles.com/lottie-editor) | 图层、颜色、文字、图片修改，透明背景与轮廓查看 | Lottie 编辑已有强供给，初期不应做完整编辑器 | 能力来自官网，未比较账户限制和实际编辑兼容率 |
| [MotionTools](https://motiontools.cn/) | 官网声明多格式预览、素材替换、信息查看和交付处理 | 与最初想法直接重叠；需要进一步用相同素材实测 | 本次未验证其准确性、隐私实现或所有格式覆盖 |
| [Spine Web Player](https://esotericsoftware.com/spine-player) | 动作与皮肤选择、时间线、速度和骨骼等调试功能 | Spine 是独立且复杂的一条检查链路，不应当成普通图片播放器 | 官方文档；版本和资源依赖需要单独处理 |
| [腾讯云礼物动画工具链](https://cloud.tencent.com/document/product/616/115992) | 预览及性能查看、多格式转换后播放 | 企业已有一体化路线；本项目可验证免登录、自部署和原格式检查的价值 | 转换后播放不等于各原始格式原生预览 |
| [AnimSuite Pro](https://www.svga.online/) | 页面声明 SVGA、VAP 本地处理，并提供转换工具入口 | 本地处理本身也已有竞品，不能当作唯一差异点 | 页面有访问令牌入口，未完成实际使用 |

**不能据此声称“市场没有同类工具”或“某竞品不支持某功能”。** 下一轮需要选 3 个最相关替代工具，使用同一份样本包对照。

## 5. 收集到的需求信号

| 证据 | 可支持的需求 | 不能推导的结论 |
| --- | --- | --- |
| PAGViewer 官方提供替换面板和性能面板 | 预览之外，动态内容与资源成本检查已有明确使用场景 | 所有团队都需要网页性能评分 |
| [VAP 官方 FAQ](https://github.com/Tencent/vap/wiki/) 记录黑边、清晰度、解码分辨率和融合预览问题 | 多背景检查、编码信息说明、融合配置诊断有依据 | 旧 FAQ 的尺寸经验值是所有设备的硬性上限 |
| [YYEVA issue 列表](https://github.com/yylive/YYEVA-Web/issues) 包含末帧停留、自适应尺寸、effects 参数和特定设备异常反馈 | 首尾帧检查、尺寸模式、动态参数可视化和环境记录值得优先验证 | 当前所有版本都有同样缺陷，或网页可自动解决设备差异 |
| LottieFiles 官网说明部分文字替换受导出字形限制 | 需展示当前文件是否可改，以及为何不能改 | 只要是 Lottie 就可以任意更改文字 |
| Spine 官方要求导出与运行时版本匹配 | 版本识别、缺失依赖检查比“自动解 ZIP”更重要 | 引入一个运行时就能支持全部 Spine 文件 |

基于这些资料，“能否播出来”只是第一步；更有价值的需求是让使用者知道：文件里有什么、当前播放器能做什么、当前异常可能在哪、同事如何复现。

## 6. 用户任务与需求优先级（初稿）

下面的 P0/P1 是结合现有证据和项目约束提出的建议，还不是经访谈确认的频率排名。

| 任务 | 主要使用者 | 建议级别 | 可验收的行为 |
| --- | --- | --- | --- |
| 收到文件，立即查看 | 设计、产品、研发、测试 | P0 | 拖入/选择文件；识别格式；不支持时明确原因，不静默失败 |
| 看动作细节 | 设计、测试 | P0 | 暂停、缩放、时间定位；有可靠支持时逐帧、倍速和区间循环；不支持的操作明确标记 |
| 查素材规格 | 研发、测试 | P0 | 尺寸、体积、时长、帧信息、格式/运行时版本；标注数据来源与未知项 |
| 检查透明与裁切 | 设计、研发 | P0 | 棋盘、黑、白、自定义背景；原始尺寸/适应画布；边界可视化 |
| 验证头像和昵称 | 设计、研发 | P0，适用格式内 | 列出真实可替换 key/索引、类型和当前值；替换、恢复；不能编辑时解释原因 |
| 发给同事复现 | 全部 | P0 的轻量版本 | 导出检查报告和配置；注明素材哈希、运行时版本、背景、时间点、替换设置；素材由双方另行传递 |
| 查看 API 如何使用 | 研发 | P1 | 与选中的真实资源绑定，显示 key、当前格式的调用示例和官方文档；不做全部 API 目录 |
| 在房间里看效果 | 设计、产品 | P1，业务假设 | 用户导入房间截图作为背景，调整礼物/头像框叠加位置；验证遮挡和比例 |
| 比较两次交付 | 设计、测试 | P1，业务假设 | A/B 同屏、时间或归一化进度对齐；不同长度明确提示；不宣称不同格式像素完全一致 |
| 一批素材快速过目 | 产品、运营、测试 | P1，频率待验证 | 多文件列表、依次切换，避免同时播放所有重素材 |
| 连送和麦位行为模拟 | 产品、研发 | P2，业务假设 | 排队、打断、叠加、动作切换；这属于业务播放策略，需独立定义 |
| 任意格式互转、压缩、改工程 | 设计、运营 | 暂缓 | 成本高、可能损失语义，偏离当前预览和检查目标 |

首版可不做全部 P0 格式能力：P0 是选定格式的基本闭环，而非要求每种格式必须同等支持每个按钮。

## 7. 各格式真正需要定义的“支持”

| 格式 | 应检查的特有内容 | 需要明确的边界 | 初步顺序 |
| --- | --- | --- | --- |
| SVGA | 声明 FPS、帧数、图片 key、sprite/资源结构、图片和文本注入 | 旧版格式、音频、具体运行时维护状态；替换预览不等于重新导出文件 | 首批候选 |
| PAG | 尺寸、时长、帧率、可编辑文字/图片索引、图层信息 | 仅暴露可编辑图层；WASM 装载和字体；预览替换与生成新 PAG 是不同能力 | 首批候选 |
| Lottie / dotLottie | 合成与图层、图片/字体依赖、文字、markers、动画集合 | 文字可能转形状或使用字形；JSON 不一定是 Lottie；容器中可能多动画 | 首批候选，dotLottie 可后置 |
| VAP | 原视频/输出画布尺寸、RGB 与 Alpha 区域、配置、动态资源 tag | VAP 与 YYEVA 不同；Web 集成通常需要配置 JSON；有时间跳转不等于精确解码到帧 | 第二批候选，若团队主用则前移 |
| YYEVA | 内嵌元数据、融合资源、透明布局、动态字段 | 独立解析及运行时；需验证定位、停止行为与资源暴露能力 | 第二批候选，按样本前移 |
| Spritesheet | 原图、网格、行列/间隔/边距、帧顺序、使用帧数 | 一张图片无法可靠推断真实 FPS 和有效帧数；标为用户配置；不规则图集需要 metadata | 成本较低的首批补充候选 |
| GIF / APNG / WebP | 真实帧数、逐帧时长、循环、透明 | 原生 img 播放不提供统一时间线；精细检查需额外解析/解码及内存控制 | 基础查看可前置，精确逐帧单独排期 |
| Spine | 骨架版本、动作、皮肤、贴图、atlas、slots、事件和混合 | JSZip 只解包；JSON/skel + atlas + 纹理配套；版本匹配、运行时许可均需核实 | 后置，除非实际素材证明高频 |

重要修正：

- YYEVA 与 VAP 是两种方案，不能写成同一格式的别名。
- GIF/APNG/WebP 不是“只能看、永远无法逐帧”；可增加解码器实现，但应评估浏览器覆盖及资源成本。[ImageDecoder 文档](https://developer.mozilla.org/en-US/docs/Web/API/ImageDecoder)明确其可以按帧解码，同时仍有浏览器兼容限制。
- 浏览器播放动图不应统一宣传成“原生硬解”；实际加速依格式、浏览器及设备而异。
- Spine 是骨骼动画，检查应以动作时长和采样时间为核心，采样帧数不能伪装为固定原始总帧数。
- 原始 FPS、浏览器渲染 FPS、视频实际呈现帧与动图平均 FPS 是不同信息，应分开命名。
- [Spine 官方许可](https://esotericsoftware.com/spine-runtimes-license)有独立集成与再分发条款；开源本项目不代表所有依赖都可按同一许可证分发。具体接入前需核对适用条款。

## 8. GitHub Pages 的产品边界

[GitHub 官方](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)将 Pages 定义为 HTML/CSS/JavaScript 静态托管。以下边界是在不额外引入服务的前提下推导的。

### 可以纳入

- 页面与运行时静态部署；素材使用本地 File/Blob 读取。
- 本地多文件、文件夹或 ZIP 导入；明确资源关联规则及缺失文件。
- Canvas/WebGL/WASM 预览、信息解析和可支持的动态替换。
- 浏览器本地保存偏好或项目配置；需要持久保存素材时应明确占用与清除方式。
- 下载截图、检查报告、可重导入的预览配置。
- 工具开源，用户可以 fork 或自行部署。

### 现阶段不纳入

- 账号、在线权限、多人实时评论、团队云空间。
- 上传私人素材后生成永久在线预览链接。
- 服务端格式转换、转码、素材扫描。
- 代理远程素材来绕过 CORS。

### “分享”的实际交付

第一版分享的是“工具网址 + 素材文件 + 检查配置/报告”。网页网址本身不包含浏览器本地素材。配置中不应默认打包头像、昵称、私有图片或素材内容；需要打包时由使用者明确选择。

远程 URL 导入不是 P0：可能受 CORS、鉴权、过期链接影响，且会触发外部请求。本地处理也不自动等于绝对无外联；字体、Lottie 图片资源、运行时 CDN 等需要明确策略。建议播放器运行时随站点发布，素材外链默认提示，由产品设计决定允许方式。

## 9. 推荐的最小产品范围

先按真实样本选择 2—3 个主格式。当前可暂以 SVGA/PAG/Lottie 为候选；如果团队礼物主用 VAP/YYEVA，应替换其中低频格式，而不是机械套用顺序。

一个可验证的闭环：

1. 导入文件，快速得到正确画面或明确错误。
2. 在统一工作区检查规格、透明、时间点。
3. 对实际存在的占位资源进行替换并恢复。
4. 导出包含环境与检查配置的记录，同事重新导入后可定位同一处。

第一版不做完整编辑器、跨格式互转、云端协作、通用性能打分或全端一致性承诺。可展示本机测量，但须记录浏览器和测量条件，不能当作 iOS/Android App 的性能结论。

## 10. 开发前的需求验证

### 样本与参与者（建议值，不是已完成调研）

- 找 6—8 位团队/朋友参与：动效设计、客户端/前端、测试/产品各至少 2 位，可一人兼岗。
- 收集 20—30 份获得使用许可的实际交付素材，统计格式、大小、资源依赖、动态字段和问题类型。
- 包含至少几份失败素材：缺图片/字体、旧格式、透明黑边、末帧异常、Spine 版本不匹配等；不能只用官方演示文件。

### 访谈与观察任务

- 最近一次收到素材时，用什么工具打开？切了几次工具？
- 哪个问题必须找设计或研发处理？能否提供真实记录？
- “看细节”具体指哪一帧、哪个位置、哪种边缘或业务行为？
- 是否经常改头像/昵称，还是偶尔才会用？是否需要多语言、长昵称、emoji？
- 手机和桌面结果不一致时，团队目前如何记录播放器版本和复现条件？
- 是否允许上传未上线素材？GitHub Pages 的访问可达性在实际网络中如何？
- 需要“导出截图/报告”，还是“别人点链接直接看”？后者和无服务器约束可能冲突。

使用现有工具完成：打开→查信息→定位细节→替换头像/文字→反馈给同事。记录耗时、失败次数、求助次数，避免只问“想不想要这个按钮”。

### 需要用数据回答的决策

| 决策 | 依据 |
| --- | --- |
| 首批支持哪几种格式 | 样本出现频率、关键业务程度和现有工具失败情况 |
| 报告导出是否 P0 | 同事复现耗时及实际交接频率 |
| 场景背景和 A/B 是否进入首版 | 多人能否举出近期具体返工案例，并在任务中实际使用 |
| 是否自行开发而非整理现成工具 | 现有工具在免登录、本地处理、开源、自部署、诊断闭环上是否存在已验证缺口 |

### 建议成功标准

首批样本都应有明确的“支持/不支持/缺依赖”结果；支持的元信息与官方工具交叉一致；导入与定位任务相对现有流程显著减少操作和求助；检查记录能让另一人复现指定状态；确认本地素材不会被未授权上传。效率目标应在测完基线后制定，不预先编造提升百分比。

## 11. 当前结论与下一步产物

已确认：可用纯静态方式实现基础检查工具，存在直接竞品，专业预览与动态内容验证有公开需求信号。

待验证：用户频次、最重要格式、语聊房叠加场景与 A/B 的实际价值、同事间报告交换是否足够。公开资料不足以证明商业规模、付费意愿或新工具的留存。

下一步先完成样本清单、竞品同素材对照和简短访谈，再输出 PRD：明确能力矩阵、页面流程、优先级、异常状态、浏览器范围、首批格式与验收标准。此后才进入工程方案。
